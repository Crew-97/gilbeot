## 0. 이 문서를 읽는 법

| 표기 | 의미 |
|---|---|
| **근거** | 기획서 v2.4의 위치. 근거 없는 기능은 이 문서에 존재하지 않는다 |
| `18-확정 N` | 기획서 18장 **MVP 정책 확정사항 표**의 N번 항목 (#1~#27, v2.4에서 #23~#27 신설) |
| `18-N` | 기획서 18장의 **하위 절** (18-1~18-7) |
| **출처** | `실동작` = 길벗이 실제로 생성·변경하는 데이터 / `Mock` = 카카오 T 트럭커 연동을 전제한 가짜 데이터 |

| `[미정: N]` | 결정 권한이 팀에 있는 항목. **에이전트·개발자가 임의로 채우지 않는다.** 목록은 14장 |

이 문서는 **당일 8시간 구현 범위**를 정의한다. 기획서에만 존재하고 이 문서에 없는 기능은 구현하지 않는 것이 정상이다.

## 1. 범위

### 1-1. 구현 범위

도착지(화물센터)와 그 주변 장소의 암묵지를 **수집 → 구조화 → 제공 → 평가 → 검수**하는 하나의 순환.

### 1-2. 제외 범위 (기능으로 만들지 않는다)

- 경로 추천 / 우회로 추천
- 도로 정보 수집 / 도로별 소요 시간
- 실시간 교통 안내
- 턴바이턴 내비게이션
- 회원가입·로그인 인증 (MVP는 단일 Mock 기사 세션)
- DB 영속화 (시드 JSON + 인메모리)

**근거**: 기획서 1, 8-3, 18-확정 22, 26 / AGENTS.md 기술 스택

### 1-3. 데이터 출처 경계

| 구분 | 항목 | 출처 |
|---|---|---|
| 트럭커 연동 전제 | 배차 정보, 위치·운행 데이터, 센터 방문 횟수, 반복 정차, **도착지 도달에 따른 운행 종료 이벤트**(`운행 종료` 버튼으로 재현), **운행 중 현재 위치**, **도착 센터 요약 정보 3종(물류 원가·머무는 시간·취급 품목)** | **Mock** |
| 길벗 생성 | 인터뷰 후보, 인터뷰, STT 원문, 지식 카드, 도움 평가, 해금, 포인트, 관리자 검수 상태 | **실동작** |

**근거**: 기획서 12-1, 18-6 (v2.4에서 트럭커 연동 목록이 늘었다)

화면에 Mock 데이터를 표시할 때는 **Mock임을 화면에 표시**한다.

| 역할 | 설명 | 진입 화면 |

| 기사 | 암묵지를 소비하고 기여하는 화물운송기사 | S-01 |

표의 순서는 **운행 여정 순서**다 (기획서 6-1). 시연 단계 번호는 기획서 20장 시연 시나리오(v2.4에서 **20단계**) 기준이다.

**화면 ID는 재번호하지 않는다.** v2.4에서 화면 2종이 여정 중간에 끼어들었지만, S-01~S-08은 `playbook/`의 빌드 프롬프트와 시연 대본이 이미 참조하고 있다. 번호를 밀면 그쪽이 전부 어긋난다. 따라서 신규 화면은 **S-09·S-10으로 뒤에 붙이고 순서만 여정에 맞춘다.**

`S-10`의 경로·명칭은 `[미정: 30]`이다. 기획서가 `커뮤니티(가칭)`로 부르고 있으며, 17장 차별점의 '커뮤니티'(게시판형)와 혼동될 수 있어 확정 명칭을 별도로 정한다. **에이전트가 임의로 이름을 정하지 않는다.**

## 5. 화면별 상세 명세

각 화면은 **정상 상태 / 빈 상태(0건) / 실패 상태**를 모두 정의한다.

**배치 순서는 ID 순이 아니라 운행 여정 순서다** (S-01 → S-02 → S-09 → S-03 → S-10 → S-04 → S-05 → S-06 → S-07 → S-08). ID를 재번호하지 않기로 했기 때문이다 (3장 참조).

### S-01 시작·가입 환영 `/`

- **목적**: 시연 시작점. 신규 가입 환영과 +100P 지급을 보여준다
- **진입**: 앱 최초 진입
- **표시 요소**: 서비스명, 한 줄 소개, 가입 환영 문구, 지급 포인트, 시작 버튼
- **사용자 액션**: `시작하기` → S-02 이동
- **상태 변화**: PNT-01 실행 → 포인트 +100, `point_transaction(signup_bonus)` 1건 생성
- **중복 방지**: 이미 `signup_bonus` 이력이 있으면 재지급하지 않고 화면만 표시
- **빈 상태**: 해당 없음
- **실패 상태**: 시드 로드 실패 시 "데이터를 불러오지 못했어요. 다시 시도해 주세요." + 재시도 버튼
- **UI 카피 예**: `길벗 가입을 환영합니다`, `+100P`

### S-02 출발지·도착지 입력 `/destination`

- **목적**: 이번 운행의 출발지와 도착 화물센터를 입력한다 (DRV-18)
- **표시 요소**
  - 출발지 입력 — **현재 위치가 기본값**이다. 시연에서는 Mock 좌표를 현재 위치로 쓴다
  - 도착지 = 화물센터 목록(이름, 지역, 등록된 암묵지 수)
  - Mock 배지
- **사용자 액션**: 센터 선택 → **S-09 도착지 브리핑**으로 이동

  - 장소별 암묵지 건수

  - 현재 포인트 잔액
- **사용자 액션**
  - 마커 선택 → 해당 장소의 카드 목록(S-04)
  - `운행 시작` 선택 → DRV-21 → `dispatch.started_at` 기록 → 운행 중 상태
  - 운행 중 커뮤니티(가칭) 화면 열기 → S-10
  - `운행 종료` 선택 → DRV-08 → 인터뷰 생성 → S-06 이동
- **상태 변화**
  - `운행 시작` 시 `dispatch.started_at` 기록
  - `운행 종료` 시 `dispatch.ended_at` 기록 + 저장된 `trigger_event` 중 **1건을 선정**해 `interview` 생성
- **핵심 규칙**
  - **`운행 종료`는 도착지 도달을 재현하는 버튼이다.** 실서비스에서는 트럭커의 위치·운행 데이터로 도달을 판정한다 (기획서 6-1 ⑥, 18-확정 14). 화면에 Mock 이벤트임을 표시한다
  - 요약 정보 3종은 **센터 운영 데이터이지 암묵지가 아니다.** 해금 대상이 아니며 Mock 배지를 붙인다. 단위는 `logisticsCost` **원** / `avgStayMinutes` **분** / `handledItems` **쉼표 구분 단일 문자열** (2026-08-13 확정, 구 미정 29). 값이 없으면 해당 줄을 비운 채 표시한다
  - 운행 중에는 **후보만 감지·저장**하고 인터뷰를 노출하지 않는다 (기획서 7-1, 7-5)
  - 후보가 복수면 **반복 횟수가 가장 많은 1건**만 인터뷰로 만든다. 동점이면 가장 최근 감지 순. **무작위 선택 금지** (기획서 7-1)
  - 선택되지 않은 후보는 인터뷰를 만들지 않는다. 다음 운행에서 재감지되므로 유실이 아니다
  - 따라서 **운행 1회 = 인터뷰 최대 1건**

```js
// 후보 선정 — 반복 횟수 내림차순, 동점이면 최근 감지 순
candidates.sort((a, b) => b.visitCount - a.visitCount || b.detectedAt - a.detectedAt)[0]
```
- **빈 상태**: 주변 장소 0건 시 "이 센터 주변에 등록된 장소가 아직 없어요." 요약 정보 값이 없으면 해당 항목만 비워 표시한다
- **실패 상태**: 지도 SDK 로드 실패 시 플레이스홀더 카드 목록으로 대체 (SYS-02)

| 센터 방문 통계 | 센터별 방문 횟수, 주변 장소 방문 횟수 | **Mock 배지 표시** |
| 암묵지 목록 | 카드별 제목·장소·카테고리·상태·작성일·👍/👎·교차 검증 수 | 실동작 |
| 카드 상세 | **원본 STT 텍스트 + AI 구조화 결과 병기** | 실동작 |
| 검토 필요 | `review` 자동 전환 카드 목록과 전환 사유 | 실동작 |
| 조치 | 유지 / 비공개 / 삭제(Soft Delete) / 검토 완료(`published` 복귀 + `reviewed_at` 기록) | 실동작 |

- **조치 결과의 기사 화면 실시간 반영 여부**: `[미정: 5]`
- **접근 제어**: 인증을 만들지 않는다 (#13 해소). 하단 메뉴에 `/admin` 링크를 노출하지 않고 시연 때 주소를 직접 입력한다

## 6. AI 파이프라인 상세 명세

`/api/structure` 하나로 처리한다. 단순 요약이 아니라 아래 4단계가 AI 활용의 핵심이다.

### 6-1. 입력

| 항목 | 설명 | 필수 |
|---|---|---|
| STT 텍스트 | 기사 음성 답변의 변환 결과 | 필수 |
| 질문 내용 | 기사에게 제시한 인터뷰 질문 | 필수 |
| 대상 장소 | 장소명·카테고리 | 필수 |
| 관련 화물센터 | 센터명 | 필수 |
| 동일 장소 기존 암묵지 목록 (`existingCards`) | 유사도 판단 대상. `published`만, 최대 20건 | 필수 |
| 이번 인터뷰에서 만든 카드 (`sessionCards`) | `duplicate` 판정용. 같은 말 반복으로 보너스를 중복 수령하는 것을 막는다 | 필수 |
| 방문·정차 시간대 | **당일 사용하지 않는다.** 프롬프트가 이 입력을 쓰지 않는다 | 제외 |

서버리스는 무상태이고 DB가 없다. 두 목록 모두 **store가 골라서 보낸다.**

**근거**: 기획서 7-3 입력, 9-5 / `docs/API.md` A-1

### 6-2. 처리 단계

| 순서 | 기능 ID | 처리 | 응답 필드 |
|---|---|---|---|
| 1 | AI-01 | 유효성 판정 (`valid` / `insufficient` / `invalid`) | `verdict`, `rejectReason` |
| 2 | AI-01, AI-05 | 카드 추출. 확인 가능한 요소만 반영, 분리 허용 | `cards` |
| 3 | AI-01 | 정보 요소 충족도 판정 | `elementCheck` |
| 4 | AI-03, AI-04 | 관계 판정 (`new`/`similar`/`conflict`/`duplicate`) | `cards[].relation` |
| 5 | AI-02 | 후속 질문 (가치 있을 때만, **최대 1개**) | `followUpQuestion` |

실패 시에는 단계별 우회 없이 **전체를 캐시 폴백으로 대체**한다 (6-6). 부분 성공을 만들면 화면 분기가 늘어난다.

### 6-3. 정보 요소 정의 (기획서 7-3 1단계)

**센터팁(`center_tip`)**: 장소 또는 화물센터 / 진입 위치·출입구 / 차량 조건 / 시간대 / 행동 또는 팁 / 이유

**주유소·식당·휴게소·쉼터(`gas`, `food`, `rest`)**: 장소 / 대형 화물차 진입·주차 가능 여부 / 이용 시점 또는 시간대 / 관련 화물센터 / 추천 또는 비추천 이유

모든 요소가 필수는 아니며, **기사 답변에서 실제로 확인할 수 있는 정보만 추출한다.**

### 6-4. 출력

```jsonc
{
  "verdict": "valid | insufficient | invalid",
  "rejectReason": null,
  "cards": [{ "title", "reason", "category", "placeName",
              "evidence", "relation", "relatedCardId", "relationReason" }],
  "elementCheck": { "요소키": true/false },   // invalid면 null
  "followUpQuestion": "질문 1개 또는 null",
  "fallbackUsed": false                       // route.js가 붙인다
}
```

| 필드 | 쓰이는 곳 |
|---|---|
| `verdict` | 유효한 암묵지 판정 5개 중 **2·3번을 AI가 판정한 결과**. 1·4·5번(STT 변환·기사 확인·게시)은 store가 판정한다 (7-2) |
| `elementCheck` | **S-06 단계 3의 O/X 화면**. 시연 8단계가 이 필드다 |
| `cards[].evidence` | 비환각 검증 근거. 관리자 화면 ADM-04 |
| `cards[].relation` | `similar`·`conflict`만 `card_relation`에 저장. `new`는 관계 없음, `duplicate`는 카드를 만들지 않는다 |
| `cards[].placeName` | **표시용.** 저장은 요청에 실어 보낸 `place.id`로 한다 |

- 빈 값은 **빈 문자열 `""`**. `null`이 아니다
- `verdict`가 `valid`가 아니면 `cards`는 빈 배열이며 보상이 없다

**근거**: `app/api/structure/route.js`의 `SYSTEM_PROMPT` 상수 (골든 테스트 **11/12**, 2026-08-13 실측) / `docs/API.md` A-2 / AGENTS.md AI 프롬프트 규칙

### 6-5. 비환각 원칙 (최우선)

| 금지 | 대신 |
|---|---|
| 원문에 없는 사실 생성·추론 | 해당 필드를 **비워서** 반환 |
| "차 세우기 괜찮아요" → "11톤 트럭까지 여유롭게 주차 가능" | 부족하면 **후속 질문** 생성 |
| 유사 판정 후 자동 병합·삭제 | **관계만 연결**, 원본 경험 보존 |

기사 말투를 유지한다. 관리자 화면에서 원본 STT와 구조화 결과를 함께 확인할 수 있게 한다.

**근거**: 기획서 7-4, 18-확정 18, 18-확정 19

### 6-6. 폴백 (P0)

`/api/structure` 응답 실패·파싱 실패·**타임아웃(20초)**·모순 응답 시 `route.js`의 `FALLBACK` 상수 캐시를 `200`으로 반환한다. 시연 중 데모가 멈추면 안 된다.

- JSON 파싱 실패는 **1회 재시도** 후 폴백
- 캐시 선택: 요청의 `sessionCards`가 비어 있으면 `base_answer`, 있으면 `follow_up_answer`
- 응답에 `fallbackUsed: true`를 붙인다. 관리자 화면 표시는 P1
- 캐시는 코드 상수로 옮긴다. 파일 읽기가 끼면 새 실패 지점이 된다
- **잘못된 요청은 폴백하지 않는다.** `400 INVALID_REQUEST`

상세는 `docs/API.md` A-6.

## 8. 지식 카드 상태 전이

### 8-1. 상태값

| 코드 | 의미 | 기사 목록 노출 |
|---|---|---|
| `draft` | AI 구조화 완료, 기사 확인 전 | 노출 안 함 |
| `published` | 게시 완료 | **노출** |
| `review` | 검토 필요로 자동 전환 | 노출 안 함 |
| `hidden` | 관리자 비공개 | 노출 안 함 |
| `deleted` | Soft Delete (물리 삭제 없음) | 노출 안 함 |

### 8-2. 전이 규칙

```text
기사 답변 → AI 구조화 → draft
  draft → (기사 확인·게시) → published
  published → (부정 평가 임계값 초과) → review
  review → (관리자 조치) → published | hidden | deleted
```

관리자 조치는 13-3 기준 **유지 / 비공개 / 삭제 / 검토 완료** 4개이며 전이는 다음과 같다.

| 조치 | 결과 상태 | 부수 효과 |
|---|---|---|
| 유지 | `published` | — |
| 비공개 | `hidden` | — |
| 삭제 | `deleted` | `deleted_at` 기록 (Soft Delete) |
| 검토 완료 | `published` | `reviewed_at` 기록 |

`검토 완료`는 **새 상태값을 만들지 않는다.** `review`에서 `published`로 되돌리고 검토 시각만 남긴다. `card_status` ENUM은 그대로 5종이다.

**근거**: 기획서 13-3 / AGENTS.md 품질

### 8-3. `review` 자동 전환 조건 (둘 중 하나 충족)

1. **도움 안 됐어요 5회 이상 누적**
2. **전체 평가 5건 이상이면서 부정 평가율 60% 이상**

평가 표본이 적을 때 부정률만으로 전환되는 것을 막기 위해 2번 조건에 최소 표본 5건을 둔다.

**근거**: 기획서 13-4, 18-확정 6

### 8-4. 시효성

모든 카드에 **작성일(`created_at`)만** 저장·표시한다. 최근확인일·자동 만료·자동 삭제는 MVP에서 사용하지 않는다.

표시 예: `작성: 2026.08.12`

**근거**: 기획서 10-4, 18-5, 18-확정 20

## 13. 구현 우선순위

당일 8시간 기준. 구현 배점 10점이며 심사는 아이디어·AI 활용 중심이라는 전제를 반영한다.

|---|---|---|
| **P0** | 시연 동선 필수 | S-01~S-09 기본 흐름, DRV-01~12·14~16·18~21, AI-01~04·06~07, PNT-01·02·04·05, ADM-01·02·04~06, SYS-01~04 |

| **P2** | 명세만 (당일 구현 제외) | 인증·로그인, DB 영속화, 자동 교차 검증, 신뢰도 랭킹, 시효성 자동 재질문, **브리핑의 AI 문단 요약**(기획서 8-4 post-MVP) |

### 13-1. v2.4로 늘어난 범위 (팀이 알고 시작해야 한다)

화면 2종(S-09·S-10)과 기능 6종(DRV-18~22, SYS-05)이 늘었다. 8시간이라는 총량은 그대로다.

- **늘어난 P0의 실제 비용은 크지 않다.** S-09 브리핑은 S-04 목록을 카테고리별로 묶어 한 화면에 배치한 것이고, DRV-20 요약 정보는 시드 값 3줄 표시, DRV-18·21은 입력과 버튼이다. **새로운 데이터 구조도, 새로운 AI 호출도 없다** (ERD v3.0에서 테이블이 늘지 않은 이유와 같다)
- **실제로 위험한 것은 S-10 하나다.** 그래서 P1에 두고, 잘라낼 때 가장 먼저 빼기로 정했다
- **AI 파이프라인(`/api/structure`)은 v2.4의 영향을 전혀 받지 않는다.** 프롬프트·응답 스키마·골든 테스트 12케이스 모두 그대로다. 해커톤 핵심 구현 장면(S-06)이 흔들리지 않는다는 뜻이다
